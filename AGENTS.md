# AGENTS.md: guide for AI coding agents (Claude Code, Cursor, Copilot, Codex, Windsurf, Aider...)

ssERP is an open-source ERP, inventory and billing app that tracks every physical unit by **serial number / IMEI**:
Vendor → Purchase → Inventory → Sale → Customer → Warranty/Service. Next.js 16 (App Router) + React 19 + TypeScript,
Drizzle ORM, PostgreSQL (Neon recommended, plain Postgres supported). MIT licensed. Money and stock records are at
stake: correctness beats speed. Read this file fully before changing code.

## Quick facts

- Node >= 20.9 (CI runs 20 and 22; `.nvmrc` = 22). Package manager: **npm** (lockfile is generated by npm 10: use `npx npm@10.9.9 install` when you change dependencies, because `npm ci` on CI uses npm 10).
- Install: `npm ci`. Dev server: `npm run dev`. First-time setup (writes `.env.local`, runs migrations, creates the admin): `npm run setup`.
- Demo data (HIK123456789 / ABC Electronics / Rahim example): `npm run seed:demo` (refuses on a non-empty company; `--force`/`--yes` rules in the script).
- Required env: `DATABASE_URL`, `AUTH_SECRET` (>= 32 chars). Web installer in production also needs `INSTALL_TOKEN` (>= 16 chars). Full table: README "Configuration" and `.env.example`. `TRUSTED_PROXY=true` only behind a proxy that overwrites forwarded headers. `DB_DRIVER=neon|pg` overrides auto-detection.
- Database driver: Neon serverless driver for `*.neon.tech` hosts, `node-postgres` otherwise (`src/server/db/driver.ts`).

## Non-negotiable invariants (reviewers check these; tests enforce several)

1. **Company scoping.** Every query on business data filters by the session's `companyId`, including joins and sub-queries. Never accept a company id from the client.
2. **Authorize first.** Every server action / route handler calls `authorize(...)` with the right permission key *before* reading input or touching the DB (`guarded()` / `guardedBranch()` in `src/server/actions/guard.ts`). Hiding UI is not security.
3. **Exact money.** No floating point for money. Parse with `src/server/money.ts`, compute in integer minor units, store `numeric(14,2)`, compute totals on the server.
4. **Lock order.** Writers of `product_units`/`stock_movements`: parent document `FOR UPDATE` → products `FOR SHARE` (sorted) → document number → unit rows `FOR UPDATE` (batched, stable order). Copy the existing order in `src/server/sales` and `src/server/purchases`.
5. **Unit status changes only through the state machine** in `src/server/serials.ts`.
6. **Migrations are append-only.** Edit the schema, run `npm run db:generate`, commit the *new* SQL file. Never edit or delete a committed migration.
7. **History.** Create/update/void/payment operations write activity-log + record-history rows in the same transaction.
8. **No secrets in logs or responses.** Never log a caught error object directly: use `safeLog` / `safeErrorInfo` from `src/server/errors.ts` (Drizzle error messages contain query params, including password hashes). `src/server/no-raw-error-logs.test.ts` enforces this.
9. **Tests are required.** Logic → `*.test.ts`. DB, locking, money or serial-state changes → `*.db.test.ts`. Bug fixes need a regression test.
10. **Public paths are an exact allow-list** (`src/server/auth/public-paths.ts`); changing it needs a test.
11. **Branch scope.** Branch-owned data is scoped via `src/server/branch.ts` (`BranchFilter` for reads, `WriteCtx` for writes; never read a branch id from the client). Every exported function of scoped modules must be classified in `src/server/branch-scope-registry.test.ts` or `npm test` fails.
12. **Cost visibility.** Do not send cost/profit values to client components unless the viewer may see them (`canSeeProfit`); omit the field on the server.
13. **Privilege rules.** Non-admins can only create/edit/assign roles whose permissions are *strictly below* their own; any permission/role/active/password change must bump `session_version` (see `src/server/iam`, `src/server/auth/revoke.ts`).
14. **No third-party theme code.** The UI shell is original; `npm run check:theme` guards it. Do not paste code from paid templates.

## Style and conventions

- TypeScript strict. Server components by default; add `"use client"` only for interactive parts. Validate all input with zod. Prefer small, pure functions with tests.
- Conventional commits (`feat:`, `fix:`, `docs:`, `ci:`, `test:`, `chore:`). Small PRs. `main` is protected: open a PR, CI must be green (6 required checks), linear history (squash merge).
- Do not add dependencies casually: pin versions, check the licence is permissive, record it in `docs/THIRD_PARTY.md`. Major upgrades of core frameworks are maintainer-only PRs (see Dependabot ignore rules).
- Keep README, wiki sources (`docs/wiki`) and CHANGELOG in sync with behaviour. Never claim something is verified when it is not (the README lists what has not been run on real infrastructure).

## Deploy playbook (for an agent asked to "deploy this")

1. **Vercel + Neon (fastest):** create a Neon project, copy the pooled connection string. Import the repo into Vercel (or use the README "Deploy" button). Set env vars `DATABASE_URL`, `AUTH_SECRET` (`openssl rand -base64 48`), `INSTALL_TOKEN` (random 16+ chars). Deploy, open `/install`, enter the token, run migrations, create the admin and company. Remove/keep `INSTALL_TOKEN` (the installer locks itself afterwards). Check `/api/health?db=1`.
2. **Local:** `./install.sh` (or `npm ci && npm run setup && npm run dev`). `npm run setup` asks for the Neon URL, generates `AUTH_SECRET`, writes `.env.local` (mode 600), migrates and seeds.
3. **Docker:** copy `.env.example` to `.env`, fill it, `docker compose up --build` (add `--profile postgres` for a bundled Postgres with `DB_DRIVER=pg`). The image has no `tsx`; migrations run via the `migrate` one-shot service/profile or `npm run db:migrate` from a checkout. The wizard needs `INSTALL_TOKEN`.
4. **Upgrading:** back up (Neon branch), then `DATABASE_URL=… npm run db:migrate` before/while deploying the new version. The admin layout shows a pending-migration banner to admins.
5. Honest status: the Neon driver path, a real Vercel deploy, the Docker image build and camera scanning on phones have not been verified end to end by the maintainers. Say so in your report; do not claim otherwise.

## When you are unsure

Read `docs/ARCHITECTURE.md`, the wiki sources in `docs/wiki/`, and `CONTRIBUTING.md`. Follow an existing pattern in the same domain folder rather than inventing a new one. If a task seems to require breaking an invariant above, stop and ask the maintainer.
